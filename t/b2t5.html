1. Introducción a los SGBD

  • SGBD (DBMS): conjunto de programas que permiten almacenar, organizar, manipular y recuperar datos de forma eficiente. Son intermediarios entre usuarios y bases de datos (lenguajes como SQL).
EtapaHito

1970-80Modelo relacional de E. F. Codd; primeros SGBD relacionales (Oracle, DB2)
1980-90Interfaces gráficas, transacciones y estándar SQL
1990-2000SGBD orientados a objetos, integración con Java
Años 2000NoSQL (escalabilidad y flexibilidad web)
ActualidadSGBD en la nube, multimodelo, Big Data
Ventajas frente a archivos planosIdea

2. Menos redundancia e inconsistenciaDatos centralizados

7. Eficiencia en consultasOptimizadores e índices
8. Escalabilidad y mantenimiento centralizadoSistemas distribuidos y nube

2. Bases de datos relacionales

2.1 Modelo relacional

  • Propuesto por E. F. Codd en 1970; estructura matemática simple: la relación (tabla).
ConceptoDefinición
RelaciónTabla que representa una entidad; nombre único, conjunto de atributos y tuplas
TuplaFila / registro: una instancia concreta
AtributoColumna / campo; mismo tipo de dato y mismo dominio
EXAMEN

Clave primaria (primary key)

Atributo o combinación de atributos que identifica de manera única cada tupla. Debe ser no nulo y único (ej.: el DNI).

ConceptoDefinición
Clave foránea (foreign key)Campo que enlaza con la clave primaria de otra tabla; garantiza la integridad referencial (ej.: id_cliente en Pedidos → Clientes)
DominioConjunto de valores válidos de un atributo (ej.: edad 0-120)
GradoNúmero de atributos (columnas) (Clientes con id, nombre, email → grado 3)
CardinalidadNúmero de tuplas (filas) (250 registros → cardinalidad 250)
  • Normalización: reduce la redundancia, asegura la integridad y mejora la eficiencia (1FN, 2FN, 3FN…).

2.2 Reglas de Codd

EXAMEN

Reglas de Codd

Formuladas por Edgar F. Codd en 1985: 13 principios (reglas 0 a 12) que debe cumplir un SGBD para considerarse plenamente relacional.

ReglaNombreDescripción
0Sistema relacionalUsar solo capacidades relacionales para gestionar datos
1Representación de la informaciónToda la información en valores en tablas
2Acceso garantizadoCada dato accesible por tabla, clave y atributo
3Tratamiento de nulosGestión lógica de valores desconocidos o no aplicables (NULL)
4Diccionario de datosCatálogo (metadatos) consultable con el mismo modelo relacional
5Lenguaje completo de datosDefinición, manipulación y control (SQL)
6Actualización mediante vistasLas vistas deben poder actualizarse si es lógicamente posible
7Manipulación en conjuntoOperaciones sobre conjuntos de registros
8Independencia físicaCambios físicos no afectan a las aplicaciones
9Independencia lógicaCambios lógicos no obligan a cambiar programas
10Integridad declarativaReglas definidas en la base de datos, no en el código
11Independencia de distribuciónIgual comportamiento centralizado o distribuido
12No subversiónNo se puede eludir el modelo relacional desde niveles bajos

2.3 Restricciones

RestricciónDescripción
DominioEl valor debe pertenecer al dominio definido
UnicidadSin valores duplicados (claves primarias y candidatas)
Nulidad (NOT NULL)Si un campo admite nulos
Clave primaria (PRIMARY KEY)Unicidad + no nulidad
Clave foránea (FOREIGN KEY)Referencia a la clave primaria de otra tabla
Integridad referencialEvita registros huérfanos (no insertar pedido con id_cliente inexistente)
Definida por el usuario (CHECK)Condiciones personalizadas: CHECK (edad >= 18)
Regla de integridadCondición
De entidadLa clave primaria debe ser única y no nula (id_cliente INT PRIMARY KEY)
ReferencialLos valores de la clave foránea deben coincidir con una clave primaria existente o ser nulos (si se permite): FOREIGN KEY (id_cliente) REFERENCES Clientes(id_cliente)
De dominioCada valor pertenece a su dominio (tipo y formato esperado)
IMPORTANTE

Dominio

Conjunto de valores válidos de un atributo. Se define por: un tipo de dato (INT, VARCHAR, DATE, BOOLEAN), una restricción lógica (edad >= 0) o un conjunto específico de valores (estado IN ('Activo', 'Inactivo')).

  • Mecanismos para aplicar el dominio: tipos de datos (VARCHAR(50)), CHECK, ENUM (MySQL), expresiones regulares (REGEXP) y procedimientos o triggers.
Restricción de BDDescripciónEjemplo
UNIQUEValores únicos aunque no sea clave primariaemail UNIQUE
DEFAULTValor por defecto si no se proporcionaestado DEFAULT 'activo'
NOT NULLObliga a que haya valornombre NOT NULL
CHECK (validación compuesta)Condiciones complejasCHECK (edad >= 18 AND pais = 'España')
  • Se aplican a nivel de columna (NOT NULL, DEFAULT, CHECK) o de tabla (UNIQUE sobre varias columnas).

2.4 Lenguaje SQL

  • SQL (Structured Query Language): estándar de las BD relacionales; desarrollado por IBM en los 70, estándar ANSI e ISO. Sintaxis declarativa: se indica qué se quiere, no cómo.
EXAMEN

Subconjuntos de SQL

DML (Data Manipulation Language)Manipulación de datosINSERT, UPDATE, DELETE
DQL (Data Query Language)Consulta de datosSELECT
DCL (Data Control Language)Control de accesoGRANT, REVOKE
TCL (Transaction Control Language)Control de transaccionesCOMMIT, ROLLBACK, SAVEPOINT

2.5 Normalización

  • Proceso teórico para organizar los datos, reducir la redundancia y garantizar la integridad, dividiendo la BD en relaciones más simples sin pérdida de información, mediante las formas normales.
Dependencia funcionalDefinición
Dependencia funcional X → Y«Y depende funcionalmente de X» o «X determina Y»: tuplas con el mismo X tienen el mismo Y
ReflexivaSi Y ⊆ X, entonces X → Y
AumentativaSi X → Y, entonces XZ → YZ
TransitivaSi X → Y e Y → Z, entonces X → Z
Forma normalCondiciónObjetivo
1FNAtributos atómicos (sin grupos repetitivos ni multivaluados)Estructura tabular
2FN1FN + sin dependencias parciales (atributos que dependen solo de parte de la clave compuesta)Separar lo que no depende de toda la clave
3FN2FN + sin dependencias transitivas (atributo que depende de otro no clave)Aislar dependencias indirectas
BCNFMás estricta que 3FN: para toda dependencia A → B, A debe ser superclaveDescomposición libre de anomalías
4FNEliminar dependencias multivaluadasSeparar valores múltiples
5FNDescompone relaciones con dependencias de unión (join dependency)Reconstrucción sin pérdida

EXAMEN

ACID

LetraPropiedadSignificado
AAtomicidadLa transacción es indivisible: se ejecuta completa o no se ejecuta; si hay fallo, se revierten los cambios
CConsistenciaLleva la BD de un estado válido a otro válido, respetando las reglas de integridad

3. Bases de datos orientadas a objetos (SGBDOO)

  • Evolución del modelo relacional que integra la programación orientada a objetos con la persistencia: almacenan objetos completos (atributos + métodos); clases, herencia, encapsulamiento y polimorfismo; cada objeto con identificador único. Útiles en ingeniería, CAD, multimedia, GIS y simulación.
IMPORTANTE

Definición de SGBDOO

Sistema de gestión de base de datos que representa la información en forma de objetos, tal y como se utilizan en la programación orientada a objetos.

EXAMEN

EncapsulamientoDatos protegidos dentro del objeto; acceso solo por métodos
ConceptoDefinición
ObjetoEntidad que encapsula datos (atributos) y comportamientos (métodos)
ClasePlantilla para crear objetos

VentajasInconvenientes

ORM (Object-Relational Mapping)

  • Técnica que mapea clases con tablas relacionales, para persistir objetos sin escribir SQL a mano. Automatiza la conversión objeto ↔ registro, hace CRUD (Crear, Leer, Actualizar, Eliminar), da portabilidad entre motores y más productividad.
  • Ejemplos: Hibernate (Java), NHibernate (C#/.NET), Entity Framework (ADO.NET, Microsoft), ActiveRecord (Ruby on Rails).
LenguajeDescripción
OQL (Object Query Language)Estándar propuesto por ODMG (Object Data Management Group); parecido a SQL pero para objetos
JPQL (Java Persistence Query Language)Con JPA o Hibernate
Extensiones OO en SGBD relacionalesOracle, PostgreSQL (tipos definidos por el usuario)
EXAMEN

OQL

Uno de los lenguajes más usados: Object Query Language, inspirado en SQL pero adaptado al paradigma orientado a objetos. Consulta objetos, colecciones, atributos complejos y relaciones jerárquicas (select, where, group by, order by) y navega atributos de tipo objeto o colección.

OID derivado de atributos (opcional)Compuesto por atributos (DNI, ID de producto); similar a una clave primaria; no sustituye al OID
ReferenciasAtributos que apuntan al OID de otro objeto (como punteros); más eficientes que las claves foráneas en relaciones complejas
Nombre simbólicoAlias para acceder al objeto (objeto_usuario['juan'])

4. Bases de datos NoSQL

  • NoSQL (Not Only SQL): nacen por el almacenamiento masivo de datos no estructurados, la escalabilidad horizontal y la disponibilidad constante (redes sociales, comercio electrónico, IoT, Big Data). Se justifican por las limitaciones de las relacionales en entornos distribuidos, la necesidad de flexibilidad de esquema, alta escalabilidad y datos heterogéneos o semiestructurados.
EXAMEN

Clasificación de las bases NoSQL

No usan el modelo relacional; ofrecen mayor escalabilidad, flexibilidad y rendimiento con grandes volúmenes y estructuras poco definidas. Se clasifican según el modelo de datos que emplean.

TipoFuncionamientoVentajasLimitacionesEjemplos
Clave-valorPares clave : valor (clave única, valor cualquier dato)Muy rápidas en lectura/escritura; cachés, sesiones y perfiles; escalabilidad horizontalNo para relaciones complejasRedis (en memoria), Riak (alta disponibilidad), Amazon DynamoDB (AWS)
DocumentalesDocumentos JSON, BSON o XMLEstructuras complejas y anidadas; consultas por campos; datos semiestructuradosPosible duplicación de datosMongoDB (el más popular), CouchDB (replicación y sincronización), RavenDB (.NET)
En columnasDatos por columnas agrupadas en familias de columnasAlto rendimiento analítico; Big Data y procesamiento por lotesMás complejas de modelarApache Cassandra, HBase (sobre Hadoop, MapReduce), ScyllaDB (compatible con Cassandra)
GrafosNodos (entidades) y aristas (relaciones)Recorrer relaciones; redes sociales, recomendaciones, rutasMenos adecuadas para cargas transaccionales simplesNeo4j (el referente), OrientDB (grafos + documentos), ArangoDB (multimodelo)
