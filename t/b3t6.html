1. Sistemas distribuidos

EXAMEN

Sistema distribuido

Conjunto de componentes software que se ejecutan en distintos equipos o entornos físicos pero cooperan para dar una funcionalidad unificada al usuario. Módulos desacoplados que se comunican por redes, servicios o protocolos estándar.

ObjetivoIdea
EscalabilidadAumentar capacidad añadiendo nodos o recursos
DisponibilidadSigue funcionando aunque fallen componentes
MantenibilidadDesplegar, actualizar o sustituir partes sin afectar al conjunto
DesempeñoParalelismo y balanceo de carga
Desacoplamiento funcionalResponsabilidades separadas en capas o servicios
  • Ejemplos: portales de atención ciudadana, ERP, comercio electrónico (microservicios), servicios sanitarios, apps móviles que consumen APIs REST en la nube.

TransparenciaDe acceso (remoto como local) · de ubicación (no hace falta saber dónde está) · de concurrencia (acceso compartido sin interferencias) · de replicación · de fallos · de movilidad (cambian de lugar sin afectar)
ConcurrenciaMúltiples procesos/usuarios simultáneos; requiere sincronización y consistencia

Independencia de heterogeneidadDistintos SO, hardware, lenguajes, redes; protocolos estándar (HTTP, gRPC, SOAP) y APIs
Compartición de recursosArchivos, BD, servicios; control de permisos y sincronización

2. Modelo cliente/servidor

  • Una o varias aplicaciones cliente envían peticiones a un servidor que las procesa y responde. Características: separación lógica de funciones, comunicación en red (TCP/IP, HTTP), multicliente, centralización del servicio, escalabilidad horizontal.
Tipo de clienteCaracterísticaEjemplo
Ligero (thin)Solo interfaz de usuario; lógica y datos en el servidorNavegador web
Pesado (thick)Parte o toda la lógica de negocio; menos comunicación pero más difícil de actualizarAplicación de escritorio con acceso directo a BD
HíbridoLógica local y delega lo pesado al servidorApps móviles, JavaScript + API REST

3. Arquitectura en capas y multicapas

  • Divide la aplicación en niveles con responsabilidad concreta. Cada capa solo se comunica con la adyacente → menos acoplamiento y más mantenibilidad. Separa interfaz, lógica y datos; promueve reutilización; facilita escalabilidad y pruebas.
ArquitecturaDescripción
2 capas (cliente/servidor)Cliente: interfaz (y parte de la lógica) · Servidor: BD y acceso a datos. Comunicación directa cliente–BD; rápida de implementar pero difícil de escalar y mantener
3 capasPresentación (UI) · Lógica de negocio (BL) · Acceso a datos (DAL)
n capasMás niveles (servicios, integración, seguridad, caché); capas en servidores distintos
MicroserviciosMódulos autónomos que se comunican por APIs (REST, gRPC, mensajería); cada uno con su propia BD y tecnología; despliegue independiente, resiliencia, escalabilidad granular
IMPORTANTE

Frontend y backend

Frontend (cliente): parte con la que interactúa el usuario; se ejecuta en el dispositivo cliente (navegador, móvil, escritorio); interfaz de usuario (HTML, CSS, JavaScript). Backend (servidor): se ejecuta en el servidor; lógica de negocio, acceso a datos y procesamiento de peticiones (API REST en Java, .NET o Python). Se comunican por HTTP/HTTPS.

Ventaja de 3 capasDescripción
Separa responsabilidadesCada capa se especializa
Mantenibilidad y trabajo colaborativoEquipos distintos por capa
EscalabilidadDespliegue y escalado independientes
ReutilizaciónUna misma API sirve a web, móvil y escritorio
  • Los microservicios se localizan por un nombre único (URL) mediante descubrimiento de servicios: Service Registry (Eureka, Consul).

4. Componentes y operación del sistema

4.1 Servidor web de aplicaciones

  • Servidor de aplicaciones: entorno de ejecución que gestiona lógica de negocio, comunicación cliente–servidor e integración con BD. Se diferencia del servidor web, que solo atiende HTTP y entrega contenido estático; el de aplicaciones procesa lógica compleja, sesiones y conexiones de BD.
TecnologíaDescripción
Servidor HTTP/SSL (TLS)Recibe peticiones HTTP y responde HTML/JSON. TLS (hoy el estándar; se sigue diciendo SSL) cifra la comunicación y protege de Man-in-the-Middle. Servidores: Apache HTTP Server (open source, Linux), Nginx (alta concurrencia y balanceo), Microsoft IIS (Windows Server)
ServletsClase Java que extiende el servidor de aplicaciones: procesa peticiones HTTP y genera respuestas dinámicas (HTML, JSON, XML); como un applet, pero en el servidor. Contenedores: Tomcat, WildFly, GlassFish
Páginas dinámicasHTML estático + código embebido (JavaScript en cliente; PHP en servidor)
JSPJava EE; código Java dentro de HTML; se compila a servlet antes de ejecutarse
ASPDe Microsoft para IIS; scripts VBScript o JavaScript; interpretado, no compilado
Intérpretes de scriptingPHP (Apache/Nginx), Python (Django, Flask), Node.js (JavaScript en servidor, tiempo real)
Frameworks de lógica de negocioSpring (inyección de componentes, REST con Spring Boot, JPA/Hibernate), Django (Python), Express.js (Node.js), Laravel (PHP), ASP.NET Core (C#)
  • Flujo de un servlet: cliente envía petición HTTP → servidor la pasa al servlet adecuado → este la procesa (BD u otros recursos) → genera respuesta dinámica y la envía.

4.2 Patrones comunes

EXAMEN

Patrón DAO

Data Access Object: patrón de diseño estructural que aísla la lógica de acceso a datos del resto de la aplicación, en especial de la lógica de negocio. Muy usado en la capa de acceso a datos (Java EE, Spring, .NET).

  • Funciones: encapsular todas las operaciones sobre la BD (consultas, inserciones, actualizaciones, eliminaciones); interfaz independiente de la tecnología de persistencia (JDBC, JPA, Hibernate, ADO.NET); cambios de BD limitados a una clase DAO; responsabilidad única.
Ventaja DAODescripción
ModularidadCambios de BD no afectan a la lógica de negocio
ReutilizaciónVarios servicios usan los mismos DAO
TestabilidadSe sustituye por mocks o stubs
MantenibilidadCódigo mejor organizado

MVC (Modelo-Vista-Controlador)

ComponenteResponsabilidad
ModeloDatos y lógica de negocio: acceso a BD, validaciones, reglas; independiente de la presentación
VistaInterfaz visible (HTML, CSS, plantillas); sin lógica de negocio
ControladorIntermediario: recibe las entradas del usuario, las interpreta, invoca al modelo y selecciona la vista
  • Flujo: usuario envía petición → controlador la recibe y valida → llama al modelo → este devuelve datos → controlador elige la vista y le pasa los datos → la vista genera la respuesta al navegador.
  • Servidor: Spring MVC, ASP.NET MVC, Django, Laravel. Cliente: Angular, React (Flux/Redux), Vue.js.

4.4 Monitorización y rendimiento

  • Detectar problemas, optimizar recursos y garantizar SLA (acuerdos de nivel de servicio).
Área a monitorizarHerramientas

5. Arquitecturas de servicios web

5.1 Servicios web

  • Funcionalidad accesible remotamente (HTTP/HTTPS) entre sistemas heterogéneos; independientes de plataforma, modulares y reutilizables. Basados en estándares abiertos (XML, JSON, HTTP, SOAP, REST); públicos, privados o internos; base de SOA y microservicios.

5.2 SOA (Service-Oriented Architecture)

  • Organiza el sistema en servicios autónomos, reutilizables e interoperables con interfaz pública y comunicación por mensajes (XML/SOAP). Integra sistemas heredados; fuerte relación con WSDL y UDDI. Caso en la Administración: Plataforma de Intermediación de Datos (PID).
EXAMEN

Componentes de SOA

ComponenteFunción
ServicioUnidad funcional autocontenida que realiza una tarea
Proveedor de serviciosDesarrolla, publica y mantiene el servicio
Consumidor de serviciosAplicación que invoca el servicio
Registro de serviciosRepositorio para publicar, descubrir y consultar metadatos; desacopla proveedor y consumidor
  • Flujo: el proveedor registra el servicio (WSDL) → el consumidor consulta el registro, lo encuentra y lo consume con un mensaje estándar → el servicio responde o ejecuta la operación.
IMPORTANTE

SOA

SOA se implementa con servicios en el backend (SOAP, REST, WSDL). Los servicios son débilmente acoplados (flexibilidad y reutilización). La definición formal de los servicios se hace con WSDL (XML).

5.3 SOAP

  • Simple Object Access Protocol: protocolo de mensajería estándar para intercambio estructurado entre aplicaciones, normalmente sobre HTTP/HTTPS (también SMTP, JMS). Adoptado por el W3C; SOAP 1.2 publicado como estándar ISO/IEC (ISO/IEC 20022-1:2004). Muy usado en entornos empresariales y gubernamentales (seguridad, transacciones, interoperabilidad, comunicación fiable).
EXAMEN

Estructura de un mensaje SOAP

Documento XML bien formado con elemento raíz <soap:Envelope>. Envelope: contenedor principal. Header (opcional): tokens de seguridad, metadatos, identificadores de transacción. Body: datos de la solicitud o respuesta (invocaciones a métodos y parámetros).

Componente SOAPFunción
WSDLLenguaje XML que describe la interfaz del servicio: métodos, tipos, ubicación y protocolos
UDDIRegistrar y descubrir servicios web; hoy en desuso
XML Schema (XSD)Estructura y tipos de datos de los mensajes; garantiza su validez
WS-SecurityEspecificación WS-(familia de estándares) para firmar, cifrar y autenticar mensajes SOAP; garantiza integridad, autenticación y confidencialidad (muy usada en la Administración)
  • WS-Security: firma digital XML (XML-Signature), cifrado (XML-Encryption), tokens de seguridad (X.509, SAML), protección de cabeceras y cuerpo. SAML: intercambio de autenticación/autorización, sobre todo en SSO.
EXAMEN

Estándares WS-* de seguridad

EstándarFunción principalResumen
WS-SecuritySeguridad a nivel de mensaje SOAPFirmar, cifrar y adjuntar tokens (usuario, SAML)
WS-SecureConversationContexto de seguridad compartidoReutiliza claves y reduce coste criptográfico en intercambios largos
WS-TrustEmitir, renovar y validar tokensSecurity Token Service (STS)
WS-FederationFederar identidades entre dominiosFacilita SSO (federación de confianza)

  • Regla mnemotécnica: Security = seguridad básica · SecureConversation = conversación segura (contexto compartido) · Trust = confianza (tokens) · Federation = identidad federada entre dominios · Policy = reglas del juego.
  • Apache Axis2: motor de servicios web open source de Apache (evolución de Axis 1.x) para construir y consumir servicios SOAP (y algo de REST); soporta SOAP, WSDL, WS-Security, WS-ReliableMessaging; APIs para Java y C; crea servicios desde POJO o WSDL; modelo modular; contenedor ligero axis2.war.

5.4 REST

  • Representational State Transfer: estilo de arquitectura de Roy Fielding (tesis doctoral, 2000); restricciones para servicios web simples, escalables y modulares usando los métodos estándar de HTTP. Todo es un recurso identificado por una URI (https://api.ejemplo.com/usuarios/123).

6. Protocolos asociados a servicios web

6.1 HTTP y HTTPS

  • HTTP: principal protocolo de transporte; modelo cliente/servidor; stateless; métodos GET, POST, PUT, DELETE, PATCH; puertos 80 (HTTP) y 443 (HTTPS). HTTPS: añade cifrado TLS (confidencialidad e integridad).
IMPORTANTE

CORS

Cross-Origin Resource Sharing: mecanismo que permite o restringe peticiones HTTP de origen cruzado hechas desde scripts del navegador (fetch(), XMLHttpRequest). Si el frontend está en un dominio distinto al backend, el navegador bloquea por defecto; el backend debe configurar cabeceras CORS indicando qué orígenes se permiten.

6.2 XML, JSON y YAML

FormatoCaracterísticas
XMLTradicional en SOAP; autodescriptivo, etiquetas jerárquicas; verboso y rígido, muy estructurado
JSONMás ligero, ideal para REST; pares clave-valor; rápido de procesar
YAMLSimilar a JSON pero más legible; usado en configuración (Docker, Kubernetes); poco usado en servicios en tiempo real

6.3 WSDL

  • Lenguaje XML que describe la interfaz pública de un servicio SOAP: operaciones, formato y tipo de mensajes, protocolos y ubicaciones.
Operación WSDLDescripción
one-wayCliente envía mensaje; el servicio no responde
request-responseCliente envía y espera respuesta
solicit-responseServicio envía y espera respuesta del cliente
notificationServicio envía al cliente sin esperar respuesta

6.4 UDDI

EXAMEN

UDDI

Universal Description, Discovery and Integration: estándar propuesto para el registro y descubrimiento de servicios web en entornos SOA. Funciona como un «directorio telefónico» de servicios. Hoy prácticamente en desuso; sustituido por portales, catálogos de API o Swagger/OpenAPI para REST.

6.5 Repaso SOAP y REST

SOAPREST
Basado en XML, rígido y estructuradoBasado en HTTP estándar, ligero y flexible
Soporta seguridad, transacciones, mensajería asíncronaJSON o XML; verbos HTTP como operación
Requiere WSDLSe describe con OpenAPI (Swagger)

6.6 gRPC y alternativas

  • gRPC (Google Remote Procedure Call): alto rendimiento; usa Protocol Buffers (protobuf) en lugar de XML/JSON; comunicación síncrona y asíncrona; streaming bidireccional; más rápido que REST en muchas operaciones.
AlternativaCaracterística
GraphQLEl cliente define exactamente qué datos quiere
WebSocketsComunicación bidireccional y persistente (tiempo real)
Server-Sent Events (SSE)Envío unidireccional y continuo servidor → cliente

7. Seguridad en sistemas distribuidos

  • Debe garantizar confidencialidad, integridad, autenticación, autorización y disponibilidad.
ConceptoDescripción
AutenticaciónVerificar la identidad (usuario/contraseña, certificados digitales, tokens)
AutorizaciónPermisos tras autenticar: RBAC (roles), ABAC (atributos), ACLs (listas de control de acceso)
HTTPSHTTP seguro con cifrado
TLSProtocolo actual (SSL obsoleto): cifrado, autenticación del servidor (y opcionalmente del cliente), integridad
Certificados digitalesEmitidos por Autoridades de Certificación (CA): verifican la identidad del servidor y establecen conexión cifrada basada en confianza
API KeysClaves estáticas que identifican/autorizan al cliente; sencillas, pero menos seguras sin HTTPS
OAuth2Protocolo estándar de delegación de autorización: acceso limitado a recursos de otro sin compartir credenciales; Access Tokens con permisos y duración limitados
JWT (JSON Web Token)Token compacto basado en JSON; 3 partes en base64: header, payload y firma; se usa con OAuth2; autocontenido (incluye usuario y permisos)

8. Tendencias actuales

TendenciaDescripción
MicroserviciosServicios pequeños e independientes con APIs ligeras (REST o gRPC); despliegue independiente, escalado individual, aislamiento de fallos, poliglotismo; facilita DevOps y despliegue continuo; reduce acoplamiento entre equipos

8.3.1 Docker

EXAMEN

Docker

Plataforma de código abierto para crear, empaquetar y desplegar aplicaciones en contenedores de forma automatizada. Un contenedor es una instancia de una imagen (paquete inmutable con código, dependencias, configuración y entorno de ejecución).

  • Ventajas: automatiza empaquetado y despliegue; portabilidad entre entornos; integración con CI/CD; aísla procesos (seguridad); compatible con Kubernetes, Docker Swarm, OpenShift.
Herramienta DockerFunción
DockerfileTexto con instrucciones para construir una imagen
docker buildGenera la imagen desde el Dockerfile
docker runEjecuta un contenedor desde una imagen
docker-composeDefine y ejecuta varios contenedores con un archivo YAML

8.3.2 Kubernetes (K8s)

  • Orquestador de contenedores creado por Google, mantenido por la CNCF (Cloud Native Computing Foundation). Despliegue, escalado, monitorización y recuperación a gran escala.
  • Funciones: balanceo de carga, escalado horizontal automático, autorreparación (auto-healing), configuración y secretos (ConfigMaps y Secrets), rolling updates y rollbacks.

NamespaceAísla recursos dentro de un clúster (entornos o equipos)
